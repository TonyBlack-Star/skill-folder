# Shopify 流量 × 销售 数据整合与看板

## 目的

把两类主键不同构的 Shopify 报表整合成「一个产品一天一行」的日度数据表，并产出可脱机打开的独立看板，之后可持续按新日期增量更新。

- **流量表**：`Day` + `Landing page path` + 访客/Sessions/加购/结账等指标（一个 path 一天一行）
- **销售表**：`Day` + `Product ID` + `Net items sold` + `Total sales`

二者主键不同构（字符串路径 vs 数字 ID），必须靠映射文件中转。

## 何时使用

- 用户说「把流量数据和销售数据整合起来」「按产品看访客和销量」
- 需要生成 Shopify 运营看板、漏斗分析、日/周/月趋势
- 已有整合结果，需要追加新日期数据

## 快速开始

```bash
# 0. 依赖
pip install openpyxl

# 1. 准备映射文件（见下节），放到数据目录

# 2. 全量整合
python scripts/integrate.py --dir <数据目录>

# 3. 生成看板（需先取 Chart.js 本地副本用于脱机兜底）
curl -L -o <数据目录>/chartjs.min.js \
  https://cdn.jsdelivr.net/npm/chart.js@4.4.7/dist/chart.umd.min.js
python scripts/make_dashboard.py --dir <数据目录>

# 4. 之后每次更新：新日期 CSV 放进 incoming/，然后
python scripts/update.py --dir <数据目录>

# 5. 生成周度/月度结论分析报告（周口径：上周五~本周四）
python scripts/weekly_report.py --dir <数据目录>
```

脚本均接受 `--dir`，默认当前目录；无任何硬编码路径，可复制到任意项目使用。

## 工作流

### 阶段 1 — 盘点与分类（先做，别跳过）

**只按表头判定文件类型，绝不按文件名。** `export (N).csv` 这类名字没有语义，且用户会不断替换文件；按编号或抽样猜分类几乎必然出错（本项目最早就把文件张冠李戴过）。

```python
含 "Landing page path" -> 流量表
含 "Product ID"        -> 销售表
两者皆无               -> 全店汇总表（无产品维度，通常无法参与产品级整合）
```

盘点时输出：每个文件的类型、行数、日期范围、产品 ID/handle 分布。若扫描结果与抽样核对不一致，以扫描脚本实际解析为准，并重读冲突文件的表头核实——**不要在文件仍在变动时下结论**，先让用户确认文件夹已定稿。

### 阶段 2 — 建立桥接映射并做双向校验

映射文件默认名为 `路径与ID匹配规则.txt`：

```
auto-heat-press-a100 | SALES | Product ID: 9870162985208
```

也支持 `handle,ID` 简写。加载后**必须做双向覆盖校验**：

- 映射中每个 handle，是否都能在流量表中找到对应路径？
- 映射中每个 Product ID，是否都能在销售表中找到对应行？

任一侧断链都会静默丢数据，校验通过才可继续。

### 阶段 3 — 清洗与聚合

**流量侧路径归一**：去 `?`/`#` → 去首尾 `/` → 剥离语言前缀（`fr-fr`/`de-de`/`en-de` 等）→ 取 `products/` 后一段为 handle。同一天可能有多个显示格式（多语言路径），归一后属同一产品，需合并。

**销售侧 ID 前向填充**：同一张销售表内 Product ID 一致，抓到该表唯一 ID 后填充其余空白单元格。一张表出现多个 ID 视为异常并上报。

**聚合到 (Day, Product ID)** —— 三类指标处理方式完全不同，这是最容易出错的地方：

| 类型 | 处理 | 示例 |
|---|---|---|
| 计数类 | 求和 | 访客、Sessions、加购数、销量、销售额 |
| 比率类 | **由合计后的分子/分母重算** | 加购率 = 总加购数 / 总 Sessions |
| 平均值类 | 按 Sessions 加权平均 | 跳出率（源表无跳出计数，近似）、平均停留时长 |

**绝不可对多个百分比取算术平均。** 例：两天 Sessions 100/900、加购 5/180，重算得 185/1000 = 18.5%，简单平均却得 (5%+20%)/2 = 12.5%。

**丢弃规则**（需与用户确认后再定）：非产品路径（`/`、`/pages/`、`/collections/`）与未命中映射的 handle，默认直接丢弃；多显示格式合并；真重复（同文件内同日同完整 path）上报而不自动合并。

### 阶段 4 — 输出

`integrated_result.xlsx`：每个产品一个 sheet，以 handle 命名（Excel 表名不允许 `/`）。第 1 行标题写完整 landing path 与 Product ID，第 2 行表头冻结，第 3 行起日度明细。比率列设 `0.00%` 格式，底层保留小数以便继续计算。

看板：套用 `assets/dashboard_template.html`（杂志风、Chart.js、含置顶的「汇总」产品）。数据以 JSON 注入 `const DATA`；Chart.js 优先 CDN，失败时启用本地副本，保证脱机可用。

### 阶段 5 — 增量更新

**基准即真相来源**：以 `integrated_result.xlsx` 为唯一历史库，不保留历史原始 CSV。

1. 新日期 CSV 放进 `incoming/`
2. `python update.py`
3. 脚本自动合并、报警，并把已处理文件归档到 `incoming/archive/`

合并语义：

- 纯新增日期 → 直接加入
- 重叠日期 → **显式报警**，且**按字段级合并**：增量只提供流量时不动销售字段，反之亦然
- 绝不静默求和

### 阶段 6 — 周/月分析报告（可选）

`weekly_report.py`：把整合结果转成**结论导向**的分析报告（非看板），输出到 `<dir>/每周分析/`。

```bash
python weekly_report.py --dir <数据目录>
```

**分层递进框架**（先理解结构 → 再做统计 → 最后挖洞察）：

| 层 | 关注点 |
|---|---|
| L0 结构 | 粒度、桥接覆盖、有流量天数占比、口径可信度 |
| L1 统计 | 水平、环比、集中度（Top1/Top3/HHI）、趋势 |
| L2 洞察 | 三因子分解、漏斗环节、产品贡献、异常检测、情景测算 |

**固定输出结构**：一句话摘要 → 数据全貌 → 核心发现（3~5 条，按重要性排序）→ 异常 → 可操作建议 → 月度分析 →（条件）当周进行中。
「当周进行中」仅当最新数据落在当前周期中途时才出现；数据刚好截止在周四时，最近周期即为完整周期，该板块自动省略。输出文件名为 `每周分析/周度分析_<周期起>_<周期止>.html`。

**时间口径（Fri–Thu）**：周维度固定为「上周五 ~ 本周四」，以周五为周期起点，**不是 ISO 自然周（周一~周日）**。推导规则：

```python
FRIDAY = 4                                  # date.weekday(): Mon=0 ... Fri=4 ... Sun=6
week_start = dt - timedelta(days=(dt.weekday() - FRIDAY) % 7)   # 该周期内的周五
```

- 最近完整周期：若 `week_start(maxd) + 6天 > maxd`，则再往前退 7 天
- 对比周：`最近完整周期起点 - 7 天`，同为周五起
- 月维度不变，仍按自然月
- 口径只由 `week_start()` 一处决定，趋势图（近 8 周）、环比、当周判断全部自动跟随；**改口径不要逐个改调用点**

**分析哲学**：

- 标题就是结论，不只列数字；每条发现必须回答 so what
- 对比产生意义：一律用环比/结构差异，而非绝对值
- 异常值最值钱：产品异动、漏斗突变、单日尖峰、归因缺口都要主动扫
- 警惕虚假精确：小样本（完成结账 < 30 单）只给方向不给精确幅度

**⚠️ 三因子分解的判因陷阱（真实踩过）**：
`Sales = Sessions × (件/会话) × 客单价` 链式分解后，**不能取"绝对值最大的因子"当主因**。
当销售额下滑而某因子为正时（例：流量 +€1,776、转化 -€1,490、客单价 -€394，净 -€107），
按绝对值会误判"下滑源于流量、应加大投放"——恰恰相反。
**正确做法：取与净变动同号且绝对值最大的因子作为主因**（代码中 `dec["主因"]`）。

**⚠️ 漏斗"最大漏点"的低价值陷阱**：
"会话→加购"几乎永远是最大漏点（电商普遍 3~5%），写进报告等于没说。
**要区分"结构性漏点"与"变化中的环节"**：若后端环节环比显著改善，则结论应是
"后端在改善、前端加购才是规模瓶颈"，并给出情景测算（加购率 +1.5pp 能多出多少单/多少销售额）。

## 必守规则（都是踩过的坑）

| 规则 | 说明 |
|---|---|
| **信表头，不信文件名** | 按编号判断文件类型必然出错 |
| **桥接先做双向校验** | handle 侧与 ID 侧各查一遍，断链要能立刻发现 |
| **比率必须重算，不能平均** | 最隐蔽的一类错误 |
| **输出产物排除在输入之外** | 否则脚本把上轮结果当数据源，销售数据被重复累加（真实发生：销量从 3 涨到 9） |
| **输出路径跟随参数，禁止硬编码** | 硬编码真实文件名会让测试污染生产数据 |
| **增量合并按字段、重叠必报警** | 整条覆盖会把缺失方清零；静默求和会翻倍 |
| **聚合逻辑只写一份** | 全量与增量共用 `etl_common.py`，避免两份逻辑分歧 |

## 零值/异常排查方法

用户问「某段时间为什么是 0」时，**先回原始 CSV 验证，不要猜**：

1. 从整合结果统计「每月有流量的天数 / 当月天数」与各产品首个有流量日期
2. 回原始流量文件，按月统计总行数与命中映射的行数
3. 检查被剔除的行（非产品路径等）是否真的全为 0

实践案例：某项目 4 月 visitors/sessions 全为 0，排查发现原始报表 4 月**根本没有任何 `/products/` 行**，只有空路径且指标全 0 的占位行——源数据如此，非整合丢失。同时发现「有销售却零落地页流量」，说明成交非由该产品页 session 归因。

## 货币与本地化

源数据通常不含币种字段，**不要臆造**。确认币种后在展示层加符号：

```bash
python scripts/make_dashboard.py --currency-symbol "€" --currency-code "EUR"
```

KPI 与表格用完整格式（`€1,234.50`），图表 Y 轴用紧凑格式（`€1.2k`）避免刻度重叠。负数显示为 `-€88.10`，不要写成 `€-88.10`。

## 验证清单

每次交付前确认：

- 分类正确（流量表数 + 销售表数 = 预期）
- 桥接双向 100% 覆盖、0 断链
- 输出行数 = 产品数 × 天数
- 异常数为 0，或异常已逐条说明
- 抽样一天：计数 = 各产品之和；比率 = 合计分子/分母
- 切周/月维度后比率仍为重算值（用独立脚本回读 XLSX 复算一遍最可靠）
- 周报周期边界正确：分析周起点必须是**周五**、终点必须是**周四**；与脚本 stdout 打印的起止日期核对
- 生成的 JS 通过 `node --check`
- 真实基准文件未被测试改动
